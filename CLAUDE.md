# Escape Velocity

A private study app for a 13-week plan (12 Oct 2026 to 10 Jan 2027; it started a week later than first planned, see HANDOFF). **`plan/escape-velocity-plan.md` is the only content source and the spec**: Part 1 is the build guide (sections 1 to 22), Parts 2 to 6 are the content. Read Part 1 before changing anything structural. `HANDOFF.md` says what is done and what is left.

## Commands

```bash
npm install
npm run compile        # plan markdown -> src/generated/*.json (fails on any plan error; run before tests/dev)
npx vitest run         # unit + Worker/D1 tests (150ish tests; ~3 s)
npx tsc --noEmit && npx tsc --noEmit -p worker/tsconfig.json
npm run build          # compile + typecheck + vite build
npx wrangler d1 migrations apply escape-velocity --local
npx wrangler dev --port 8787 --local                 # serves dist/ + the API on http://localhost:8787
npm run test:e2e                                     # Playwright: builds, serves dist/ on :8788 with its own D1, resets it per test
```

E2E in a container that has its own Chromium: `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium E2E_SKIP_BUILD=1 npx playwright test <spec>` (see README). Screenshot baselines are per platform and are **not in git** (`e2e/*-snapshots/` is ignored): create them with `--update-snapshots` on the machine that will run them.

`.dev.vars` (git-ignored) must contain `ENVIRONMENT=dev` and `OWNER_EMAIL=dev@localhost` for local dev: that is the only Access bypass.

## Architecture in one paragraph

Preact + Signals + `preact-iso`, Vite, TypeScript. Local-first: every change is an **op** (desired state, never a toggle or delta) with a UUID `opId`; it is applied locally (`src/lib/reduce.ts`), saved to IndexedDB with an outbox (`src/lib/store.ts`), then sent by `src/lib/sync.ts` to `POST /api/ops` (max 20 per request). The Hono Worker (`worker/`) validates with zod, applies each request in one `DB.batch`, and skips already-applied `opId`s (`applied_op`). D1 schema is `migrations/0001_init.sql` (append-only: add `0002_...`, never edit). Content is compiled from the markdown by `scripts/lib/compile.ts` into small JSON chunks (core, one per week, one per page) so Today loads almost nothing.

## Rules that are easy to break

- **Dates**: only `src/lib/dates.ts` does date maths; "today" is a `YYYY-MM-DD` string in Asia/Kolkata; never `new Date('YYYY-MM-DD')`. **The day ends at 04:00 Kolkata, not midnight** (`DAY_STARTS_HOUR`): `kolkataToday()` shifts the clock back four hours, so work at 01:30 counts for the day before (ticks, logged and solved problems, sessions, streaks, flashcard days, the weekly points, the AI daily cap all follow). Never format a date with `Intl` yourself: call `kolkataToday(instant)`. Between 00:00 and 03:59 Today says so (`isLateNight`).
- **Points are derived** (`src/lib/points.ts`), never stored. Readiness items are worth 0.
- **Client reducer and Worker must agree**: `tests/worker/parity.test.ts` runs the same ops through both. Change both together.
- **No offline cache, no PWA.** The owner wants changes to show the moment the page is reloaded, so there is no service worker, manifest or precache, and performance budgets are not enforced. `public/sw.js` is only a kill switch for browsers that still have the old worker, and `main.tsx` also removes it. Hashed assets are cached by HTTP (`public/_headers`), `index.html` never. Local-first data (IndexedDB + outbox) stays: it is data safety, not asset caching. Keep the app light anyway, but do not trade features or clarity for kilobytes. zod still loads on idle (`loadValidator`).
- **Task IDs (`w04-07`, `r-03`) are permanent keys and are never shown.** Show `taskLabel(id)` ("Week 4 · Task 7") or `refLabel(ref)` from `src/lib/plan.ts`.
- **Avoid layout shift.** `main.tsx` waits (at most 300 ms; 600 ms on a device with no local copy, which also waits for the first sync) for the first screen's content chunk before rendering; components read `weekLoaded`/`pageLoaded` synchronously. The Today side column and day rail are lazy panels (`lazyPage`, which has `.preload()`), preloaded in the same wait, with space reserved. `content-visibility: auto` is only on rows below the first screenful (it shifts the page otherwise). `.stack` has one shrinkable column (`minmax(0, 1fr)`) so a wide child cannot stretch a page past the screen.
- **Accessibility**: single-choice chip sets are `role="group"` with `aria-pressed` buttons (never `role="radio"` plus `aria-pressed`); options in the palette hold text, not buttons. axe runs on every page, theme and dialog.
- **Solved problems** (Progress, Solved problems tab): `GET /api/solved` (`worker/solved.ts`) reads the owner's solved questions live from AlgoTracker's Neon database (secret `ALGOTRACKER_DATABASE_URL`, var `ALGOTRACKER_EMAIL`) with one read-only SELECT; nothing is copied into D1. Same rule as the tracker: done AND `solved_at` set, day = the Kolkata date of `solved_at`. The page groups by the tracker's topic, newest group and newest problem first, and adds problems logged here with a link (under "Logged here") unless AlgoTracker already has that link (`canonicalProblemUrl`). The e2e server blanks the secret (`--var ALGOTRACKER_DATABASE_URL:`) and uses `POST /api/dev/solved` (dev only) to pretend the database answered. Never put the connection string in a committed file.
- **Solved problems feed everything** (`src/lib/problems.ts`): `mergeProblems` joins AlgoTracker's solved problems with the ones logged here (same link counts once; AlgoTracker day = Kolkata date of `solved_at`) and the scorecard, charts, ready check, streak and DSA tasks all read that one list. A DSA task is **done by itself** when the day has enough solved problems, any difficulty (`PlanTask.solve`, parsed from the task text by `dsaSolve` in the compiler: one-day tasks need their lowest number, weekly ones one problem on each listed weekday, light days skipped). It is derived, not an op: `engine.autoDoneSet` is added to `engine.doneSet`, the tick is locked (`aria-disabled`, toast says why), and it drops out the moment a problem is un-solved. AlgoTracker is read once on open (`readSolvedOnOpen`) and again only when a Refresh button (Today, Solved problems) is pressed: nothing polls it, and returning to the tab does not read it.
- **No polling, and every server call is accounted for.** Opening the page costs `GET /api/state` + `GET /api/solved`; a local change costs one `POST /api/ops` and nothing else (`sync.run(false)`: push only, the server did what the op said); the state is pulled again only on open, when the network returns, and after the server refuses an op. The look (theme) is this device's own and costs no call at all (localStorage only). No `setInterval`, no timers, nothing on tab focus; another device's changes arrive on reload. `e2e/sync.spec.ts` counts the calls per action: when you add a feature, add what it costs there.
- **Study links** (plan Part 6, "Study resources", also kept as `escape-velocity-resources.md`): the compiler parses the "Resources by week" table into `ResourceRow`s and fails on an unknown kind or access, a bad link, a design not in the library, or a week/day with no task. Each row goes to the one task on that day it fits (its design, then words from the task, then the task type: LLD rows to the machine-coding task, Docker/Kubernetes/AWS rows to the infra task), into `WeekChunk.resources[taskId]`; all rows are in `library.resources` (design pages pick theirs by `designId`; `/sources` and the Library Resources tab list them by week via `StudyLinks`). Free first and, inside that, videos before docs before code (the owner learns best from video, see the table's `Min` column for video length; a long course links to its chapter with `&t=…s`). Rows whose topic starts `Maths:`, `Capstone:`, `DSA:`, `Mock(s):` or `Story:` go to the task of that type on that day. Premium shown with a lock, partial tagged "intro free". Every task with links has at least one video (unit test; a paper task needs its free doc instead, and a video where a good one exists). Every premium or partial doc must have a free way in (checked in `tests/unit/compiler.test.ts`). All links were checked live on 5 Oct 2026 (YouTube titles via oEmbed); Medium and Razorpay Engineering answer bots with 403 but open in a browser.
- **The BenQ RD270Q (27", 2560x1440, 144 Hz, about 109 ppi)** is a target screen (`e2e/benq.spec.ts`): from 2300 px wide the page is up to 2200 px (`--page-max`) with 300 / 540 px side columns, the top bar lines up with the page, the root font is 18 px from 2200 px, and dialogs are wider. Library opens this week's design in the side panel instead of leaving it empty. For 144 Hz nothing animates in JS faster than it must: the constellation twinkle is capped at about 30 fps (`FRAME_MS`), scrolling costs about 1 ms of main thread a frame (measured), and everything else is CSS on the compositor. `engine.allProblems` / `engine.problemsByDay` merge the solved problems once per change; do not recompute them per row.
- **AI search** (`worker/ask.ts`, `worker/pinecone.ts`, `src/ui/Palette.tsx`, README "AI search"): the box searches locally first (`src/lib/search.ts`: word-aware, typo-tolerant, ranked, instant, offline); "Ask" is explicit (`?` or ⌘↵), never on keystrokes. The Worker builds context from the box's candidates + the bundled corpus (`src/generated/rag.json`, built by `scripts/lib/rag.ts`, plan content only) + Pinecone (integrated embedding, one namespace per content hash), asks OpenAI for JSON, and **drops any id it did not offer** and any action not in the catalogue; actions are rows the person confirms. Chunk ids are palette entry ids, so answers map to real rows. Daily cap in D1. e2e blanks the keys (`--var OPENAI_API_KEY: --var PINECONE_API_KEY:`) and mocks `/api/ask`; Worker tests mock `fetch`. When the plan changes, rebuild the index (Settings). Never put a key in a file.
- **Search is measured, not guessed** (`tests/golden/`, `npm run eval:search`, `e2e/crawl.spec.ts`): about 130 golden questions with the palette entry ids that answer them; the scorer reports recall@k, MRR and bootstrap intervals for the box (rows in the order shown) and for what `worker/retrieve.ts` would hand the model, and a unit test holds the committed baseline (`eval:search:update` ratchets it). Change search, keywords, the corpus or the prompt only with a before and after number. Every page, tab and part of a page that a link reaches needs a `PAGES`/`SECTIONS` row (the crawl spec fails otherwise), and every `PAGES`/`SECTIONS` row gets a corpus chunk automatically (`scripts/lib/rag.ts`), or the AI could never cite it. Do not cache AI answers: provider prompt caching (static prefix first) is the safe saving. The AI is bounded: `inScope` (`worker/retrieve.ts`) declines foreign questions before any call, the model must set `in_scope`, the prompt carries 10 chunks, and the action catalogue only goes with a command; change those only with `npm run eval:search` numbers (and `tests/golden/scope.ts`).
- **Time-shaped motivation** (`src/lib/rhythm.ts`, `src/ui/Rhythm.tsx`, `src/lib/priority.ts`): chapters, time left today (`TYPE_MINUTES` are estimates), "Only have a little time?" (`fitInto`), the Monday fresh-start card with "If … then …" plans (a free note `plan:wNN`, hidden from the Free notes and Recent lists), the rest note after six active days, the Momentum card on Progress, and Core/Fintech tiers for designs. Keep it quiet and honest: weeks not days for streaks, no loss warnings, no animation, every line computed from real data (`e2e/rhythm.spec.ts`). Saving a plan costs one `POST /api/ops` like any note.
- **Headers and CSP** (`public/_headers`, `e2e/headers.spec.ts`): no inline script (the theme init is `public/theme-init.js`), scripts only from self and the YouTube player, no framing. If you add a third-party script, image or frame, add it to the CSP and run the headers spec. Toasts can carry one action (`say(message, ms, { label, run })`, used for Undo after logging a problem). Restore (`src/lib/restore.ts`) and the calendar (`src/lib/calendar.ts`) are in Settings.
- **One timer, in the top bar** (`src/tools/TimerChip.tsx`): idle it is a Start menu (`TIMER_CHOICES`), running it shows the time, the kind (or "Time’s up" / "Past the box") and one action (Stop, Finish, Log it, Close). There is deliberately no second timer card in any page, and no Restart button. The tab title carries the countdown. Tests find it with `header.topbar` + `getByRole('group', { name: 'Timer in the top bar' })`.
- **Cabin, the focus sound** (`src/tools/focusSound.ts`, `src/tools/sound/` (`catalog.ts` has the names), `src/ui/SoundPicker.tsx`, `SoundGlyph.tsx`, `SoundLine.tsx`, the sound menu in `src/tools/TimerChip.tsx`, Settings → Cabin sound): the app's name for its focus sound is **Cabin** (`BRAND`), and each sound has a name of its own with what it is under it: Engine hum (brown noise, id `brown`), Cabin air (pink, `pink`), Monsoon (rain, `rain`), Ridge wind (`wind`), Tide (generated waves, `ocean`), Forest (the recorded playlist, `nature`), and My sound (`custom`: a pasted link the owner can name, up to 40 characters). Ids are what is saved; only the names change in `catalog.ts`. A `SoundSource` (generated noise via Web Audio, or a hosted stream in a hidden 1px player via the IFrame API) starts from `startTimer` (the click is what lets the browser play) and fades out in `stopTimer`/`dismissTimer`/finish. **Switching is a crossfade** (`setFocusSettings` → `begin(true)`; the old source fades out 1.4 s while the new one fades in) and a mute survives a switch. It is reachable from the Start menu (a select), the running chip (a sound menu: what is playing, volume, a list, a link to Settings; the speaker button beside it still mutes), the `m` key, a `Sound: …` row per sound in the search box (`action:sound:<id>`, plus a live Mute/Unmute row), Settings (a card per sound with its own Hear button), a "with Monsoon · change" line on Today's hero and the timer page, and the system media controls (titled with the sound's name, artist "Cabin · Escape Velocity"). The owner chose to hide where the nature playlist comes from and has YouTube Premium (so the player uses www.youtube.com, not the nocookie host, so Premium applies and there are no ads): UI labels never say YouTube, and a stream that cannot play (embedding off, removed) falls back to Engine hum and says why in Settings. The bars beside the sound menu move while it plays and are still in Paper and with reduced motion. Settings are device-local (`ev:focus-sound`: source, volume, custom link, custom name), never synced. e2e stubs the player script (`e2e/focus-sound.spec.ts`).
- **Extras, derive-first and the gap check** (plan Part 5: Papers, Equation bank, Gap check; `src/pages/LibraryPapers.tsx`, `LibraryGaps.tsx`, `src/ui/Equation.tsx`, `src/tools/FormulaTool.tsx`, `src/ui/Sketches.tsx`): `paper` tasks (Friday night, from week 3) and bonus equations (a `maths` task with an equation-bank row) are **optional** (`PlanTask.optional`): listed, never the next action (`pickNextUp`), left out of "n of m done" (`coreTasks`) and out of a light week's star. None sits in a Puja week (1, 2) and week 1's Friday night stays off; a compiler test holds this. A maths task is **derive-first**: `question ‖ check: answer` is split by the compiler, the check lives in `WeekChunk.checks` and shows only behind `Peek` (never locked: "Show it anyway"). Shelf equations have no task and are ticked as `eq-NN` (the schema and the Worker accept them: `shelfIds`). A paper's decision cards use `designId = paper-<task id>` (the Worker allows it); equation answers and paper summaries are free notes `eq:<id>` and `paper:<task id>`, left out of the Free notes list. The ten gap tasks end in `Why:` (flashcards) and carry a `sketch` from the gap table; a sketch is a small SVG drawn with `src/ui/diagram.tsx`, loaded lazily, and shown after you have written your answer (`SketchPeek` in the why-note) or openly on the Gap check tab. Task ids in the gap, paper and equation tables are shown as "Week 4 · Task 7" links, never raw. New diagrams: add the id to `shared/sketches.ts`, draw it in `Sketches.tsx`, name it in the gap table.
- **Light days keep going, and a missed day waits** (`src/lib/today.ts`: `onLightDay`, `pickLight`, `waitingFor`): front matter `light_days` (Durga Puja 17 to 21 Oct, Kali Puja/Diwali 8 Nov) have no points target, but nothing stops: every task planned for those days must carry ` ‖ light: the small version` (the compiler splits it into `WeekChunk.tasks[id].light`, `PlanTask.hasLight`; a unit test fails if a light-day task has none). On a light day Today's hero offers the lightest undone task's small version (`LIGHT_RANK`), task rows show it first with "Full version" behind a click, and work done on a light day counts as activity (`missedDays` checks activity before skipping light days). A missed day loses nothing: "Waiting for you" on Today (hidden on light days and in the welcome-back restart) lists the undone core tasks of earlier days this week and of last week, most points first, three at a time; never extras, the daily DSA or rest notes. `pickNextUp` still never looks back.
- **The boss problem** is explained from the plan's `### The boss problem` (under the DSA track; `pages.weeks.bossHtml`): `BossHow` on the boss task row and Today hero, the Guide, and the DSA track page (`/weeks/dsa#boss`). Change the steps in the plan only.
- **Links must land** (`src/lib/anchor.ts`, `e2e/routing.spec.ts`, `e2e/destinations.spec.ts`): every "#part" link goes through `followHash`, which waits up to 20 s for the target (pages and chunks load lazily), keeps checking so an element with the same id on the page you are leaving (the Guide and the DSA track both have `#boss`) never wins, puts the target back in view when content loads above it (Safari has no scroll anchoring) until you scroll, click or press a key, and marks it (`data-hit`). A palette row is `closeOverlay()` then `navigate(url)`; a readiness item (`r-03`) is on Progress (`/progress#r-03`), never in a week; external links open through a real `<a target=_blank>` click (not `window.open`, which can be blocked). After an AI answer the cursor is on the first suggested action when there is one, so "press Enter to confirm" confirms that action. When you add anything the AI or the box can name, give it a place in `destinations.ts`, give the element an `id`, and run the two specs: `routing.spec.ts` clicks every kind of row from another page and checks where you land.
- **Flashcard day**: the day a card was last reviewed comes from its schedule (`lastReviewedOn`), not from the server's `updatedAt`, so a review made offline and synced the next day still counts for the day it was made.
- **Design**: warm and motivating, few words, details behind links. Tokens in `src/theme/tokens.css` (`--accent` amber on night, ember on cream; `--done` green is only ever "done"; `--surface-2` for quiet fills). Cards use `var(--radius)`. The glossary (`src/pages/glossary.ts`) explains every plan term; task-type tags, capstone chips and pages link to `/guide#<id>`. The capstone page has an SVG architecture diagram (`src/ui/CapstoneDiagram.tsx`) drawn from the plan's Flow line, and the compiler reads the capstone bullets into `capstoneFacts`.
- **Themes**: Paper (the default for a browser that has never picked one), Paper night, Light, Dark, System; keys 1 to 5 in that order. Paper night is Paper in a dark tone: `data-theme` stays `paper` and `data-tone="night"` swaps the tokens (warm off-black `#15130f`, off-white ink `#efe9d9`, a muted line), so every Paper rule still applies. Paper has no animation, shadow, gradient or blur, and every border is solid (so the masthead rule is a solid 2px line, never `double`; light days are marked by a moon icon and words); `e2e/paper.spec.ts` checks every element's computed style in both tones. Never rely on colour alone (the BenQ ePaper mode is greyscale): done/today/light day also differ by icon, weight or pattern. The saved choice lives in localStorage (`ev:theme`) and wins over the synced setting. Paper is tuned for long reading: a sheet on a desk (`--bg` the warm desk, `--surface` the lighter sheet used by cards, dialogs and inputs, no shadow), soft ink at 12 to 14 : 1 (not black, muted text 7 : 1 or more), Literata (self-hosted, open licence, preloaded, `font-display: optional`) as the body face, 17px root (18px from 2200px), line height 1.68 (1.76 at night). Do not go back to pure black or white.
- **Prepared statements only** in the Worker; user notes are always rendered as text, never HTML.
- Tool versions are newer than most docs: Vite 8, TypeScript 7, Preact 11, Vitest **4.x** (pinned: `@cloudflare/vitest-pool-workers` needs `^4.1`), zod 4 (`zod/mini` on the client). Check the installed package's types/README before assuming an API.
- Worker tests run on an older workerd than wrangler: `vitest.config.ts` uses compatibility date 2026-08-01, `wrangler.jsonc` keeps 2026-10-01.
- **E2E gotchas**: The browser runs in Los Angeles time on purpose. Lazy chunks (the note editor, the guide) need the network, so a test that goes offline opens what it needs first. After an axe scan or a dialog closes, reset focus before pressing keys. Do not run two Playwright commands at once: they share one database.
- Node 26's experimental global `localStorage` breaks happy-dom tests; `tests/unit/setup.ts` shims it.
